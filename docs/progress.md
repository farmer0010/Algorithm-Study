## Lv.4 진입 판단 (Day 127 기준 — 보류로 정정)
- 이전 판단(Day 126 기준 "다음 주 초반 안정성 관찰 후 적극 검토 가능")을 **보류**로 정정함.
- **Day 127 실측 근거:**
    - 문제당 코드 제출 왕복 횟수가 여전히 많음 (Problem 1 다익스트라: 약 9~10회, Problem 3 플로이드 응용: 약 5~6회).
    - "그래프형 배열 크기는 정점 수 + 1로 잡아야 한다"는 원칙을, Problem 1(배달)에서 이미 지적받아 고쳤음에도 **같은 세션의 Problem 3(순위)에서 다시 놓치고**, 그마저도 한 번에 못 고치고 두 번 더 지적받은 뒤에야 정정함.
    - `n`/`N` 대소문자 변수명 오류가 Problem 1 안에서만 3턴 연속 반복됨.
- **결론:** 알고리즘 "패턴 인식"(어떤 문제에 어떤 알고리즘을 써야 할지 감 잡기)은 안정적으로 자리 잡았으나, "구현 자동화"(경계 조건·배열 크기 같은 디테일을 지적받기 전에 스스로 먼저 챙기는 습관)는 아직 미성숙한 단계. 새 알고리즘 개념을 더 밀어붙이기보다, 당분간 Lv.2~3 문제 반복을 통해 구현 자동화 구간을 먼저 다지는 것이 우선.

### Lv.4 진입 재검토 기준 (구체화 — 아래 3가지 확인되면 재검토)
1. 새로운 그래프형 문제를 처음 마주쳤을 때, 배열 크기를 지적 없이 스스로 n+1로 잡는 것이 **2~3세션 연속**으로 확인될 것
2. 한 문제당 코드 제출 왕복이 평균 **3~4회 이내**로 줄어들 것 (컴파일 에러성 실수는 거의 사라지고, 로직 디테일 정도만 남는 수준)
3. **같은 세션 안에서** 동일한 지적(변수명, 배열 크기, 경계 조건 등)을 두 번 이상 반복해서 받지 않을 것

## 최근 취약 포인트 (누적 추적용)
- **그래프형 배열 크기 설계 실수 (반복 재발, 우선 관찰 대상):** 정점 번호가 1~n일 때 배열 크기를 n+1로 잡아야 한다는 원칙을, 같은 세션 안에서도 여러 번(Day 127, Problem 1 다익스트라 → Problem 3 순위) 스스로 못 잡고 반복 지적받음. "그래프 문제 시작 = 배열 크기 n+1부터 체크"를 의식적 루틴으로 만들 필요. → Lv.4 진입 재검토 기준의 핵심 관찰 항목.
- **대칭 관계 단방향 체크 누락 (신규):** "순위" 문제에서 `battle[i][j]`(이김)만 확인하고 `battle[j][i]`(짐)를 빠뜨려 하위권 선수의 순위 확정을 놓칠 뻔함. 양방향/대칭 관계를 다루는 카운팅 로직에서는 항상 반대 방향 조건(`||`)까지 챙겨야 함.
- **인터페이스/생성자 문법 혼동 (신규, 새 문법 도입 초반 특유):** `implements Comparable` 대신 `implements compareTo`로 오기, `compareTo` 대신 `compare`로 오기, `new Node(...)` 대신 `Node(...)`로 `new` 키워드 누락 등 — PriorityQueue/Comparable을 처음 쓸 때 유사한 이름의 표준 API끼리 헷갈리는 경향. 다음에 새 문법 도입 시 정확한 인터페이스/메서드 시그니처를 먼저 확인하고 코드 작성하는 습관 필요.
- if-else 배타적 분기 처리: 독립된 if문을 여러 개 나열하면 한 문자/조건이 중복으로 여러 블록에 걸릴 수 있음 (Day 123, 괄호 회전하기 / Day 124, 두 큐 합 같게 만들기에서 반복 확인 — if/if → if/else if 전환 필요). Day 127 "가장 큰 정사각형 찾기"에서는 우연히 안전했으나 구조적 위험은 동일하게 남아있음.
- 코드 신뢰보다 검증 우선: 최적화된 코드라도 실제 예제 값으로 직접 트레이싱해서 검증하는 습관 필요 (Day 123, 택배 배달과 수거하기 / Day 124, 호텔 대실 / Day 125, 카펫).
- 경계 조건(등호) 민감도: `>=`와 `>`, `<`와 `<=` 하나 차이로 정답/오답이 갈리는 경우가 반복됨 (Day 124, 호텔 대실 / Day 125, 입국심사 / Day 127, 순위 — 배열 크기·반복 범위에서 n번째 원소를 빠뜨리는 형태로 재발).
- 상태 동기화 누락: 값을 한쪽에서 다른 쪽으로 옮기는 로직에서, 받는 쪽만 갱신하고 내주는 쪽 갱신을 빠뜨리는 실수 (Day 124, 두 큐 합 같게 만들기 — sum1/sum2 동시 갱신 누락).
- for문 증감식/변수명 오타로 인한 무한루프·컴파일 에러: 조건식의 변수와 증감식의 변수가 다르게 타이핑되는 실수, 혹은 대소문자가 다른 변수명(`n` vs `N`)을 혼용하는 실수가 반복 재발 중 (Day 124, 파괴되지 않은 건물 / Day 126, 합승 택시 요금 / Day 127, 배달 — 3턴 연속 `n`/`N` 혼용). 코드 작성 직후 변수명·조건·증감식을 눈으로 재확인하는 습관을 의식적으로 체화할 필요.
- 다차원 배열 인덱스 범위 혼동: N×M이 정사각형이 아닐 때 행/열 반복 범위(n, m)를 서로 바꿔 쓰는 실수 (Day 124, 파괴되지 않은 건물).
- 이분 탐색 종료 조건/경계 이동 방향 착오 (Day 125, 입국심사 — 무관한 변수로 while 조건 설정, `left`/`right` 갱신 방향 혼동).
- 조건 반전 실수: 새로운 개념 도입 시, 조건이 참/거짓일 때 각각 무엇을 해야 하는지가 뒤바뀌는 실수 (Day 126, 정수 삼각형 / 섬 연결하기의 `union()` boolean 리턴 로직).
