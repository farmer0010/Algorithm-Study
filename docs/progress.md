## 최근 취약 포인트 (누적 추적용)
- if-else 배타적 분기 처리: 독립된 if문을 여러 개 나열하면 한 문자/조건이 중복으로 여러 블록에 걸릴 수 있음 (Day 123, 괄호 회전하기 / Day 124, 두 큐 합 같게 만들기에서 반복 확인 — if/if → if/else if 전환 필요).
- 코드 신뢰보다 검증 우선: 최적화된 코드라도 실제 예제 값으로 직접 트레이싱해서 검증하는 습관 필요 (Day 123, 택배 배달과 수거하기 / Day 124, 호텔 대실 / Day 125, 카펫 — total%h==0 체크 없이도 안전한지 브루트포스로 직접 검증).
- 직관적으로 재현 가능한 코드 선호: 압축된 수식형 최적해보다, 손으로 시뮬레이션 가능한 코드가 실전에서 더 안전하다는 점을 확인함.
- 경계 조건(등호) 민감도: `>=`와 `>` 하나 차이로 정답/오답이 갈리는 경우가 반복됨 (Day 124, 호텔 대실 — 청소 종료 시각과 다음 입실 시각이 같을 때 처리 / Day 125, 입국심사 — person==n을 놓치지 않으려면 `>`가 아닌 `>=`로 처리해야 함, 동일 패턴 재확인).
- 상태 동기화 누락: 값을 한쪽에서 다른 쪽으로 옮기는 로직에서, 받는 쪽만 갱신하고 내주는 쪽 갱신을 빠뜨리는 실수 (Day 124, 두 큐 합 같게 만들기 — sum1/sum2 동시 갱신 누락).
- for문 증감식 오타로 인한 무한루프/컴파일 에러: 조건식의 변수와 증감식의 변수가 다르게 타이핑되는 실수가 반복 재발 중 (Day 124, 파괴되지 않은 건물 — for(i=1; i<=n; j++) / Day 126, 합승 택시 요금 — for(k=1; k<=n; j++)). 코드 작성 직후 조건/증감 변수 일치 여부를 눈으로 재확인하는 습관을 의식적으로 체화할 필요.
- 다차원 배열 인덱스 범위 혼동: N×M이 정사각형이 아닐 때 행/열 반복 범위(n, m)를 서로 바꿔 쓰는 실수 (Day 124, 파괴되지 않은 건물).
- 이분 탐색 종료 조건 설계 오류: 탐색 범위(`left`/`right`)가 아니라 무관한 변수(예: `n`)를 while 조건으로 사용해 무한루프를 유발한 사례 (Day 125, 입국심사).
- 이분 탐색 경계 이동 방향 착오: "충분함/부족함" 판단은 맞게 했는데, 옮겨야 할 변수(`left` vs `right`)를 헷갈려 반대쪽을 건드리는 실수 (Day 125, 입국심사 — `person < n`(부족)일 때 `right`를 갱신하는 오류. `left = mid + 1`로 고쳐야 했음).
- 조건 반전 실수 (신규): 새로운 개념 도입 시, 조건이 참/거짓일 때 각각 무엇을 해야 하는지가 뒤바뀌는 실수가 두 군데서 발생 (Day 126, 정수 삼각형 — 위/아래층 참조 방향(`i-1` vs `i+1`) 혼동 / Day 126, 섬 연결하기 — `union()`의 boolean 리턴 로직이 반대로 설계됨: "같은 그룹이면 true, 다른 그룹이면 false"로 짰다가 "같은 그룹이면 false(다리 불필요), 다른 그룹이면 true(합쳐짐)"로 정정). 새 개념을 배울 때 "이 조건이 참일 때 정확히 무엇을 해야 하는지"를 코드로 옮기기 전에 말로 먼저 정리하는 습관이 필요함.
- 재귀 함수의 return 값 누락/오반환 (신규): `find()` 함수 작성 중, 재귀 호출 결과(`find(parent[x])`)를 호출만 하고 반환을 안 하거나, 재귀와 무관한 엉뚱한 값(`x`)을 리턴하는 실수가 반복됨 (Day 126, 섬 연결하기). 재귀 함수 작성 시 "이 재귀 호출의 결과를 그대로 밖으로 전달해야 하는가?"를 항상 자문할 것.
