- **부정적 신호:** 순위 검색(Lv.2)에서는 다수 왕복 발생. 다만 이번 왕복의 성격은 Day 127과 다름 — "이미 배운 실수 패턴의 재발"이 아니라 "재귀 기반 조합 생성 + 해시맵 전처리"라는 **처음 다뤄보는 설계 패턴 자체에 대한 이해 부족**에서 온 왕복이 대부분. 다만 세션 내에서 "원본 문자열 vs split 결과 배열 인덱싱 혼동"(`str[4]` vs `str_info[4]`)이 2~3턴에 걸쳐 반복 지적됨 — 이는 새로운 변수를 만든 뒤에도 이전 변수를 관성적으로 계속 참조하는 패턴으로, 기존 "변수명 혼용" 계열 취약점과 궤를 같이함.
- **결론:** 그래프형 배열 크기(n+1) 관련 문제가 이번 세션엔 없어서 재검토 기준 1번은 판단 보류. 기준 2번(왕복 3~4회 이내)은 신규 아이디 추천만 충족, 순위 검색은 미충족. 기준 3번(동일 지적 반복 금지)은 "str vs str_info" 건으로 미충족. **Lv.4 진입은 계속 보류.** 다만 "쉬운 문제에서의 정교함"은 뚜렷이 개선되고 있으므로, 다음 세션(단어 변환)에서 재귀/BFS 재응용 시 왕복 횟수를 계속 관찰할 것.

## 최근 취약 포인트 (누적 추적용)
- **원본 문자열 vs split 결과 배열 인덱싱 혼동 (신규, Day 128):** 문자열을 `split()`해서 새 배열(`str_info`)에 담아둔 뒤에도, 이후 코드에서 원본 변수(`str`)를 계속 인덱싱하려는 실수가 한 문제 안에서 3회 이상 반복됨 (`query_str` 생성부는 맞게 고쳤으나 `target` 파싱, `count()` 호출부에서 재발). 새 변수를 만든 시점에 "이제부터는 이 변수만 써야 한다"를 의식적으로 표시하는 습관 필요.
- **Map 조회 API 선택 혼동 (신규, Day 128):** `get`(없으면 null) / `getOrDefault`(없으면 지정 기본값) / `computeIfAbsent`(없으면 생성 후 저장까지) 세 가지의 차이를 처음엔 구분하지 못해 `get()` 결과를 그대로 다음 메서드에 넘겼다가 NullPointerException 유발. "이 Key가 항상 존재를 보장받는가?"를 먼저 판단하고 API를 고르는 습관 필요.
- **낯선 문법/API 최초 사용 시 문법 오류 다발 (재발, 계열 강화):** `computeIfAbsent`를 처음 쓸 때 괄호 불일치, 제네릭 파라미터 위치 오류(`Map<String, List<Integer> map>`), 메서드 체이닝 위치 착오(`.add()`가 람다 안으로 들어감) 등 문법 오류가 여러 턴에 걸쳐 반복됨. Day 127의 "PriorityQueue/Comparable 처음 쓸 때 시그니처 혼동"과 같은 계열 — 새 API를 쓰기 전에 정확한 사용 예시를 먼저 한 번 손으로 써보고 시작하는 루틴 필요.
- **그래프형 배열 크기 설계 실수 (관찰 지속, Day 128 해당 없음):** 이번 세션엔 그래프 문제가 없어 재발 여부 확인 불가. 다음 그래프 문제에서 계속 관찰.
- **대칭 관계 단방향 체크 누락 (Day 127 발견):** 관찰 지속.
- **if-else 배타적 분기 처리:** Day 128 신규 아이디 추천에서는 오히려 "동시에 일어날 수 있는 조건은 if/if로 분리해야 한다"를 정확히 구분해서 적용함 — 개선 신호로 기록.
- 코드 신뢰보다 검증 우선, 경계 조건(등호) 민감도, 상태 동기화 누락, for문 증감식/변수명 오타, 다차원 배열 인덱스 범위 혼동, 이분 탐색 종료 조건/경계 이동 방향 착오(Day 128에서도 `left += 1` 대신 `left = mid + 1`로 정확히 짚어 개선 확인됨), 조건 반전 실수, 재귀 함수 return 값 누락 — 기존 항목 유지, Day 128에서 이분 탐색 갱신 방향은 오히려 개선 신호 확인.
